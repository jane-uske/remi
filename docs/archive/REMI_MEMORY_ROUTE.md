# REMI_MEMORY_ROUTE.md

## 这份文档回答什么

这份文档只回答 4 个问题：
- Remi 的记忆到底是为了解什么问题
- 为什么不能靠“把更多历史塞进上下文”解决
- AI 伴侣为什么不该把工具调用做成主价值
- 实时语音里，`我想想…` 这种表现该怎么和真实内部链路对应起来

它不是 schema 文档，也不是实现细节说明；那些应继续以 `MEMORY_V2_DESIGN.md`、`PIPELINE.md` 和实际代码为准。

---

## 一句话

**Remi 的记忆路线，不是“带更多字给模型”，而是“先把这轮真正重要的东西挑出来，再让她像同一个人一样说出来”。**

---

## 1. Remi 的记忆不是为了什么

Remi 的记忆，不是为了：
- 做一个事实数据库
- 让模型每轮读更多历史
- 让 prompt 越来越长
- 和通用 AI 比“谁记得更多”

这些方向都会把产品拉回“更强的通用助手”路线。

而 Remi 如果只是“另一个也会记忆的 AI”，就没有存在意义。

---

## 2. Remi 的记忆是为了解什么

Remi 的记忆真正服务的是：

### A. 关系连续性
用户回来时，Remi 还能像同一个人一样接上。

### B. 当前重点保持
在短上下文和低推理强度下，Remi 仍然知道：
- 这轮到底在处理什么
- 什么是新约束
- 什么不能踩
- 应该先接哪条线

### C. 严肃时刻不出戏
轻松闲聊、睡前陪伴、现实压力倾诉切换时，记忆和当前上下文必须帮助她稳住，而不是继续飘。

---

## 3. 为什么不能靠“更多上下文”解决

如果只做这件事：
- 把最近几轮裁一裁
- 塞进 prompt
- 让低推理 LLM 自己猜重点

那上限会很低：
- 一长就漂
- 一复杂就失焦
- 一补充现实约束就容易忘前面重点
- 一旦历史里混太多无关内容，短上下文很快报废

所以真正的问题不是：
- 1000 字太短

真正的问题是：
- **这 1000 字是不是经过重点提纯**

### 核心原则
- 短上下文不是问题
- **短而不精选才是问题**

人类不会在脑海里过 1000 个字才说话；
但人会先抓重点。

Remi 该学的不是“带更多历史”，而是“先知道这轮什么最重要”。

---

## 4. Remi 更合理的记忆分层

### 第一层：会话上下文（短）
用途：
- 维持当前真实对话的连续性
- 服务当前这次响应

特点：
- 只保留最近几轮
- 必须短
- 为实时性让路

### 第二层：当前上下文 / working memory（短但精选）
用途：
- 当前这几轮到底在处理什么
- 用户刚刚补了什么新条件
- 哪个主题被 veto 了
- 哪件事是这轮不能忘的

特点：
- 不是长期保存一切
- 是本轮重点聚焦层

### 第三层：长期关系记忆（按需检索）
用途：
- 长期事实
- 关系主线
- recurring episode
- 未完话题
- 情绪与关系轨迹

特点：
- 不应每轮全量注入
- 只在相关时召回

---

## 5. 记忆路线里真正决定上限的东西

不是 prompt 长度本身。
而是下面这 4 件事：

### A. 当前轮意图判断
这一轮到底是：
- 闲聊
- 情绪分享
- 要判断
- 现实约束更新
- 不想继续聊某个话题

### B. 当前上下文提纯
本轮只带：
- 当前在处理的那条线
- 刚刚更新的现实条件
- 当前不能踩的边界

### C. 长期记忆相关性筛选
只带最 relevant 的：
- 当前最相关的长期主线
- 当前未完的话题
- 真正会影响这次回应的事实

### D. 回复约束前置
先把本轮规则明确：
- 先答还是先接住
- 能不能问
- 能问几个
- 不要轻浮
- 不要主持腔

所以 Remi 的记忆路线，本质上不是“更会存”，而是：
**更会挑。**

---

## 6. AI 伴侣为什么不该把工具调用做成主价值

作为 AI 伴侣，用户来找 Remi，主要不是为了：
- 查天气
- 跑复杂工作流
- 做多步 agent 执行
- 搜资料
- 管一堆插件

用户来找 Remi，更主要是为了：
- 被陪着
- 被记住
- 被接住
- 感觉她在
- 感觉她还是她

所以：

### 工具应该少、克制、隐身
适合的能力：
- 时间类
- 记忆类
- 少量现实辅助

### 工具不该抢主线
不适合当前产品定位的方向：
- 大量搜索
- 复杂 agent 工作流
- 大而全插件生态
- 把“什么都能做”当作主卖点

### 原则
**工具只服务陪伴，不重写产品分类。**

一旦工具味太重，用户就会重新问：
> 那我为什么不直接找 ChatGPT / 豆包？

---

## 7. 实时语音里，“我想想…” 应该怎么成立

`我想想…` 可以有。
但不能是假装思考。

如果 Remi 说：
- “我想想。”
- “等一下，我捋一下。”
- “我回一下刚刚那条线。”

那背后应该真的在做：
- 查 memory
- 查 working memory
- 查时间 / 日期 recap
- 更新 decision context
- 整理当前约束

### 错误链路
- 先让大模型整段想完
- 再让它决定要不要调工具
- 再整段播 TTS

这会很慢，也很像 agent。

### 更合理的链路
1. **轻路由判断**
   - 这是闲聊、判断、回忆，还是要查时间/recap
2. **短占位句**（如果真的需要）
   - “我想想。”
   - “等一下，我捋一下。”
3. **后台并行检索 / 能力直连**
4. **主回复生成**
   - LLM 负责把结果说得像她
5. **分段流式 TTS**
   - 首句先出，后续边生成边播

### 核心原则
在伴侣主链路里，优先：
- 系统先判
- 能力直连
- LLM 负责把结果说得像她

而不是：
- 让主 LLM 在语音主链路里像 agent 一样多轮 deciding tool use

---

## 8. 对当前实现的约束

结合当前项目状态，后续任何“记忆优化”都应先问：

- 这是不是在帮助 Remi 更像同一个人？
- 这是不是在帮助短上下文条件下抓重点？
- 这会不会把主链路重新做成通用 agent？
- 这会不会拖慢实时性，损伤“像真人接话”的感觉？

如果答案不够清晰，就不该进入主线程。

---

## 9. 最短结论

Remi 的记忆路线不是“越多越好”，而是：

- **短上下文保实时**
- **当前上下文保重点**
- **长期记忆按需检索**
- **工具调用最小化且隐身**
- **LLM 负责把结果说得像她，而不是像 agent**

这才是 AI 伴侣路线，而不是通用助手路线。
