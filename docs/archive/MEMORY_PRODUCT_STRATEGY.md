# MEMORY_PRODUCT_STRATEGY.md

## 这份文档回答什么

这份文档只回答 6 个问题：
- Remi 为什么需要记忆
- Remi 的记忆不该做成什么
- Remi 的记忆应该分哪几层
- 短上下文条件下，什么决定交流上限
- AI 伴侣的工具边界是什么
- 实时语音里“我想想…”该怎么和真实系统动作绑定

它不是数据库 schema 文档，也不是实现细节清单。实现细节继续以 `MEMORY_V2_DESIGN.md`、`REMI_MEMORY_ROUTE.md`、`CURRENT_FOCUS.md` 和实际代码为准。

---

## 一句话

**Remi 的记忆，不是为了让模型看更多历史，而是为了让用户感觉“她还是她”。**

再具体一点：
- 不是“事实仓库”优先
- 不是“上下文越长越好”优先
- 是**关系连续性、当前重点、严肃时刻不出戏**优先

---

## 为什么 Remi 需要记忆

如果 Remi 没有记忆，她就会退化成：
- 每轮重置的聊天框
- 每次都像第一次见面的系统
- 轻松时能聊，复杂一点就失焦
- 严肃时刻容易说错、忘刚说过的重点、破坏关系感

Remi 的记忆真正要解决的是：

### 1. 关系连续性
用户回来时，她还能像同一个人一样接上。

### 2. 当前重点保持
在短上下文、低推理强度下，她依然知道：
- 这轮到底在处理什么
- 用户刚补了什么现实约束
- 哪个点不能踩
- 应该先接哪条线

### 3. 严肃时刻不出戏
当用户从轻松闲聊切到现实压力、财务压力、自责、委屈时，记忆和当前上下文能帮她稳住，而不是继续轻飘飘接错。

---

## Remi 的记忆不该做成什么

### 1. 不该做成“更多历史塞进 prompt”
如果只是：
- 裁一裁最近历史
- 塞给模型
- 让模型自己猜重点

那上限会很低。

问题不是 1000 字短。
问题是：
**这 1000 字里如果混了太多不重要的内容，就已经废了。**

### 2. 不该做成“事实数据库优先”
伴侣产品里，记忆的核心不是“记得更多事实”，而是：
- 记得关系主线
- 记得当前重点
- 记得哪些话没说完
- 记得哪些现实约束已经改变了判断

### 3. 不该做成“每轮全量召回”
长期记忆不应该每轮都全塞给模型。
那会让：
- prompt 更长
- 首 token 更慢
- 语音更不像人
- 回复更像系统在翻档案

## Remi 的记忆分层

更准确地说，Remi 的记忆应该分成 **热 / 温 / 冷** 三层。

### 热层：会话上下文 + Working Memory
用途：
- 维持当前真实对话连续性
- 服务当前这次响应
- 把这轮最重要的主线、现实约束和禁区保留下来

特点：
- 只保留最近几轮和当前重点
- 必须短、快、精选
- 决定这轮接话会不会掉线

### 温层：Episode / Unresolved / 关系主线
用途：
- 保存长期关系事件
- 保存未完话题和 recurring episode
- 在 relevant 时把“这条生活主线还没过去”召回给模型

特点：
- 不该每轮全量注入
- 只在相关时召回
- 目标是“像同一个人”，不是“像档案系统”

### 冷层：Archive Ledger / Replay / Offline 整理
用途：
- 保留原始流水、审计、回放和离线重算材料
- 为 episode 重抽、脏数据复核、长期治理提供底座

特点：
- 冷层本体不是“每天一篇日记”
- 日记或日报只能是冷层的派生产物
- 冷层主要服务治理、回放和后验质量提升，而不是每轮 prompt 注入

### 当前真实状态
- 热层：已有雏形，但边界还不够硬
- 温层：主链路已接通，但事件表达还很粗
- 冷层：只有原材料和回放基础，还没真正成型

### 当前最重要的判断
当前不是“继续把记忆做得更宽”。
当前更重要的是：
- 把热层做稳
- 把温层表达做厚一点
- 补最小冷层治理底座

## 什么决定短上下文下的交流上限

不是 prompt 长度本身。
真正决定上限的是这 4 件事：

### 1. 当前轮意图判断
这一轮到底是：
- 闲聊
- 情绪分享
- 要判断
- 现实约束更新
- 不想继续聊某个话题
- 嫌你老问

### 2. 当前上下文提纯
本轮只带：
- 当前正在处理的那条线
- 刚刚更新的现实条件
- 当前不能踩的边界

### 3. 长期记忆相关性筛选
只带最 relevant 的：
- 当前最相关的长期主线
- 当前未完的话题
- 真正会影响这次回应的事实

### 4. 回复约束前置
先把这轮规则说清：
- 先答还是先接住
- 能不能问
- 能问几个
- 不要轻浮
- 不要主持腔

### 核心原则
- 短上下文不是问题
- **短而不精选才是问题**

人类不会脑海里过 1000 个字才说话；
但人会先抓重点。

Remi 该学的不是“带更多历史”，而是：
**先知道这轮什么最重要。**

## 记忆路线和当前主线的关系

当前项目已经证明：
- Memory V2 主链路已接通
- episode 写路径、读路径、proactive planner 已具备骨架

所以当前不该继续把主线理解成：
- 更多 recall
- 更多 hygiene 规则
- 更多 audit 扩展

当前真正主线应该是：

**把记忆变成用户能感受到的可靠感。**

也就是：
- 刚说过的事实别掉
- 用户一转严肃场景别飘
- 昨天和今天能自然接上
- 默认人格别因为记忆接法变化而漂移

## AI 伴侣的工具边界

作为 AI 伴侣，工具调用不是主价值。

用户来找 Remi，主要不是为了：
- 查天气
- 跑复杂工作流
- 做多步 agent 执行
- 搜资料
- 管一堆插件

用户来找 Remi，更主要是为了：
- 被陪着
- 被记住
- 被接住
- 感觉她在
- 感觉她还是她

### 因此，工具应该：少、克制、隐身
适合保留的能力：
- 时间类
- 记忆类
- 少量现实辅助

### 工具不该抢主线
不适合当前定位的方向：
- 大量搜索
- 复杂 agent 工作流
- 大而全插件生态
- 用“什么都能做”当主卖点

### 原则
**工具只服务陪伴，不重写产品分类。**

一旦工具味太重，用户就会重新问：
> 那我为什么不直接找 ChatGPT / 豆包？

## 实时语音里的“我想想…”

`我想想…` 可以有。
但不能是假装思考。

如果 Remi 说：
- “我想想。”
- “等一下，我捋一下。”
- “我回一下刚刚那条线。”

那背后应该真的在做：
- 查 memory
- 查 working memory
- 查时间 / 日期 recap
- 更新 decision context
- 整理当前约束

### 错误链路
- 先让大模型整段想完
- 再让它决定要不要调工具
- 再整段播 TTS

这会很慢，也很像 agent。

### 更合理的链路
1. **系统先给预算和上下文**
   - 当前是语音还是文本
   - 当前延迟预算大概是多少
   - 需要哪些精选上下文和 recall
2. **短占位句**（只有真的走慢路径时才允许）
   - “我想想。”
   - “等一下，我捋一下。”
3. **后台并行检索 / 能力直连**
4. **主回复生成**
   - LLM 负责理解灰区、决定怎么答、把结果说得像她
5. **分段流式 TTS**
   - 首句先出，后续边生成边播

### 核心原则
在伴侣主链路里，优先：
- 系统给预算、边界和精选上下文
- 需要时做能力直连
- LLM 负责主要理解和表达

而不是：
- 让系统自己做一层越来越重的“问题解释器”
- 让主 LLM 在语音主链路里像 agent 一样多轮 deciding tool use

---

## 主 LLM 请求预算

### 默认规则
- 语音主链路：默认 **fast budget**
- 文本主链路：默认 **normal budget**
- 只有少数高价值回合才升到 **deliberate budget**

### 允许例外的情况
- 用户显式要求“认真想想 / 别急着答”
- 需要 relevant recall / tool / 时间回顾
- 严肃现实判断或高风险场景
- 不懂会明显跑偏

### 原则
**预算档可以变，但系统不该为了选预算而自己变成一个小模型。**

伴侣链路要像人，不能像 agent，也不能像规则堆出来的代理。

---

## 系统和 LLM 的边界

### 系统该负责什么
- 当前交互模式与延迟预算
- 当前上下文提纯
- recall / tool / safety 的硬边界
- 极少数明显、稳定、可枚举的信号
- 回复约束前置

### LLM 该负责什么
- 主要语境理解
- 直接答还是先想一下再答
- 微妙上下文和灰区判断
- 风格表达
- 把结果说得像她

### 一句话边界
**系统给预算和上下文，LLM 做主要理解；规则只保硬边界，不代替模型思考。**

### 当前明确不该继续做的事
- 不要继续把坏样本直接补进 runtime 主逻辑
- 不要继续扩越来越厚的 case-specific 规则
- 不要为了“判断思考深度”再造一层复杂解释器

## 多语言策略

不要把中文规则翻译一遍就叫多语言。

更合理的是三层：

### 1. 语言无关层
- 时间请求
- 回顾请求
- 输入长度
- 标点强度
- 当前上下文连续性
- 风险等级

### 2. 语言包层
按语言维护：
- veto 表达
- answer-now 表达
- 常见判断句
- 常见情绪词
- 少量高频口语

### 3. 灰区交给 LLM
尤其是：
- 新梗
- 反讽
- 黑话
- 文化暗示
- 混合语言

### 原则
**主逻辑通用化，规则语言包化，灰区交给 LLM。**

## 未来服务路线下，记忆模块该支持什么

如果 Remi 未来走的是：
- 固定人格陪伴服务
- 关系连续性服务
- 夜间 / 日常缝隙陪伴服务
- 少量隐身能力服务

那记忆模块最该支持的是：

### 1. 关系连续性
回来时像同一个人。

### 2. 当前重点稳定
短上下文下仍然抓得住重点。

### 3. 严肃时刻可靠
别在高重量场景里忘重点、踩边界、说轻浮话。

### 4. 低打扰 recall
不是每轮大张旗鼓翻档案，而是在该想起的时候自然想起。

## 当前哪些旧判断已经算错信息

下面这些现在应视为错误方向：
- “把更多历史塞给模型就能解决记忆问题”
- “AI 伴侣的核心价值是会调用更多工具”
- “主 LLM 在语音主链路里像 agent 一样多轮 decide tool use 是合理方向”
- “只要底层链路接通，体验自然会成立”
- “Memory 模块现在最该继续向宽和深扩”

---

## 最短结论

Remi 的记忆产品策略不是：
- 越多越好
- 越全越好
- 越像通用助手越好

而是：
- **短上下文保实时**
- **当前上下文保重点**
- **长期记忆按需检索**
- **工具调用最小化且隐身**
- **LLM 负责把结果说得像她，而不是像 agent**

这才是 AI 伴侣路线，而不是通用助手路线。
